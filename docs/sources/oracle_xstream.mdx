title: Oracle XStream Source
description: "Stream committed row changes from Oracle Database into an Iggy stream through XStream Out, with at-least-once delivery."
---

The Oracle XStream source connector streams committed row changes (`INSERT`, `UPDATE`, `DELETE`) from Oracle Database into an Iggy stream. An XStream Out outbound server inside the database captures changes from the redo log, assembles whole transactions and delivers them in commit order. The connector is the client of that outbound server. Delivery is at-least-once: the connector tells Oracle that a change is processed only after the runtime has acknowledged the batch.

Target: Oracle 19c Enterprise Edition and later, multitenant (CDB) and non-CDB.

**Licence.** Oracle documents that the XStream APIs require a license for the Oracle GoldenGate product. Every user of this connector needs it. The Oracle client library is loaded at run time and is never redistributed with Iggy.

This page is a curated subset of the documentation. The canonical reference, including the database setup, is the [oracle_xstream_source README](https://github.com/apache/iggy-connectors/tree/master/sources/oracle_xstream_source) in the `apache/iggy-connectors` repository.

## Requirements

- An outbound server that a DBA created. The connector never runs DDL.
- Oracle Instant Client (Basic) on the host that runs the connectors runtime, and `libaio` on Linux.
- `DIAG_SIGHANDLER_ENABLED=FALSE` in the client's `sqlnet.ora`. Without it, the first OCI call installs signal handlers for `SIGINT`, `SIGQUIT`, `SIGILL`, `SIGTRAP`, `SIGABRT`, `SIGFPE`, `SIGXCPU`, `SIGXFSZ` and `SIGSYS` in the runtime process.
- The database in `ARCHIVELOG` mode, and supplemental logging on the captured tables (`ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS` for full before images on updates).
- A schema rule on the outbound server if new tables must be captured. A table rule misses `CREATE TABLE` of new tables and stops following a renamed table.

## Configuration

Use the broker credentials and main runtime configuration from the [source guide](/docs/connectors/sources/source#configuration). Build the plugin from the checkout root:

```bash
cargo build --release -p iggy_connector_oracle_xstream_source
```

Save this entry in the runtime's connector directory. Create the stream and topic first, and fill in the connection and outbound server values.

```toml
type = "source"
key = "oracle"
enabled = true
version = 0
name = "Oracle source"
path = "target/release/libiggy_connector_oracle_xstream_source"
plugin_config_format = "toml"

[[streams]]
stream = "oracle"
topic = "changes"
schema = "json"
batch_length = 1000
linger_time = "5ms"

[plugin_config]
connect_string = "dbhost:1521/ORCLCDB"
username = "c##xstrmadmin"
password = "change-me"
outbound_server = "IGGY_XOUT"
tables = ["APP.ORDERS"]
```

### Options

| Option | Type | Default | Description |
| ------ | ---- | ------- | ----------- |
| `connect_string` | string | **required** | Easy Connect string of the CDB root service |
| `username` | string | **required** | User that ran `CREATE_OUTBOUND` |
| `password` | string | **required** | Secret. Not logged |
| `outbound_server` | string | **required** | Outbound server name, at most 30 bytes |
| `oci_library_path` | string | platform default | Path of `libclntsh` |
| `tables` | list | all captured tables | `OWNER.TABLE` names or `OWNER.*`, which also covers tables created later |
| `poll_interval` | string | `100ms` | Pause before each poll |
| `poll_budget` | string | `500ms` | Time a poll may spend collecting a batch when the stream is busy. An idle receive blocks for 1 to 2 seconds regardless |
| `max_batch_events` | u32 | `1000` | Changes (rows and schema changes) per batch |
| `reattach_backoff` | string | `5s` | Pause before re-attaching after a stale session (`ORA-26812`) or an unreachable database |
| `max_reattach_attempts` | u32 | `5` | Attempt limit for re-attaching |
| `verbose_logging` | bool | `false` | Log every batch |

## Messages

The connector produces one Iggy message per row change, in Oracle commit order within a partition. Set `partition_id = 0` on the stream, or use a topic with one partition: without it the runtime spreads messages over the partitions of an existing topic and the commit order is lost. The headers `table` and `op` carry the table name and the operation (`insert`, `update`, `delete` or `ddl`).

```json
{
  "table": "APP.ORDERS",
  "op": "update",
  "position": "00000000001934F7...",
  "xid": "10.25.831",
  "source_time": "2026-11-25T10:11:12",
  "before": {"ID": 7, "STATUS": "NEW"},
  "after": {"ID": 7, "STATUS": "SHIPPED"}
}
```

The message id is derived from the transaction id and the number of the change inside the transaction. The number keeps counting when a large transaction spans several batches, and a replay carries the same ids. Row messages carry exactly the columns of their change record. Apply a schema change to the target when its message arrives.

## Schema changes

A DDL statement on a captured table never stops the connector. `COMMENT`, `CREATE INDEX` and `GRANT OBJECT` are skipped. Everything else is forwarded in stream order as one message with `op` set to `ddl`, the Oracle `command` and the `statement` text, and without `before` or `after`. This covers `ALTER TABLE`, `CREATE TABLE`, `TRUNCATE TABLE`, `DROP TABLE` and `RENAME`. The consumer decides what to do with them.

Stopping on DDL is not offered, because Oracle replays the DDL record after a restart.

## Delivery and state

- A batch is staged until the runtime acknowledges it. On acknowledgement the connector saves its checkpoint and tells Oracle the processed low position, which lets the database purge redo it no longer needs.
- On a negative acknowledgement, the same batch is sent again from memory without detaching from the outbound server.
- A batch that fills in the middle of a transaction ends there. Its acknowledgement does not move the low position into the open transaction, so a crash replays that whole transaction.
- Unacknowledged transactions are replayed in full after a restart, a killed runtime or a lost session.
- If Oracle reports that the saved position is below its processed low position (`ORA-21560`), the connector attaches once more without a position and the outbound server picks its own start. Changes between the two positions are not replayed.
- A checkpoint written for another outbound server or another version fails the connector at start. Undecodable state starts from the outbound server's own position.

## Limits

- `NUMBER`, `VARCHAR2`, `NVARCHAR2`, `CHAR`, `NCHAR`, `DATE`, `TIMESTAMP` (with and without time zone), `RAW`, `BINARY_FLOAT` and `BINARY_DOUBLE` are forwarded. A forwarded row with any other column type (LOB, `LONG`, `XMLType`, `INTERVAL`, `ROWID`) ends the poll there. The commits read before it are delivered and acknowledged, then the connector stops with an error that names the table and column. The changes of the transaction that holds the row are not delivered, and they are replayed when the connector is started again after the column is removed or the table is excluded. Rows of tables excluded by `tables` are skipped and never stop the connector.
- There is no initial snapshot. The stream starts at the outbound server's position.
- Not tested: Standard Edition 2, RAC, Data Guard and managed cloud databases.
